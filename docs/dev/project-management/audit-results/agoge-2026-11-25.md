## Finding 1 of 18: HIGH. A filter driver with a non-UTF-8 name still runs during `snapshot` and `compare`

**What.** The snapshot script promises never to run the target repo's filter programs. It finds them with a `git config --get-regexp` regex, and in a UTF-8 locale that regex does not match a driver name that holds an invalid UTF-8 byte. Such a driver is not overridden, so git runs it. Trudy found it (security lane).

**Evidence (confirmed).** The probe configured `filter.x\377y.clean` (pointing at a marker script) with `required=true` and attributed `*.txt` to it. After a same-size edit, `target_snapshot.py snapshot` returned rc=0 and the marker read `ran filter`. `compare` did the same. Under `LC_ALL=C` the marker stayed `none`. `_filter_overrides()` returned only `filter.lfs.*`. Controls `Ev.il`, `A=B` and `UPPER` were all blocked.

**If unchanged.** A target repo can run a program of its choice on every agoge integrity check. That is the exact vector the 0.3.1 fix closed. The defect is stable, but every run against an untrusted repo is exposed. It also makes the CHANGELOG claim false.

**Options.**
1. **Discover on bytes.** List config with `git config --includes --null --name-only --list`, select the `filter.` keys in Python on bytes, and keep the names as bytes or surrogateescape through to `GIT_CONFIG_KEY_n`. Benefit: removes the regex and locale dependence entirely. Drawback: touches the env-building path. Effort: S-M. Could break: drivers with odd bytes in the generated `GIT_CONFIG_KEY` values; test on Linux CI too.
2. **Run discovery under `LC_ALL=C`.** Benefit: a one-line env change. Drawback: still trusts the regex, and any other locale-sensitive path stays. Effort: S. Could break: nothing visible (C locale only changes matching).
3. **Accept or defer.** Benefit: none. Drawback: the security promise stays broken.

**Recommendation: option 1.** It closes the class (regex discovery), not one locale. Against it: it is more code than option 2, and the non-UTF-8 test needs care on APFS (the config key is fine, but a test that also needs a non-UTF-8 path will skip). Regression test: `filter.x\377y.clean` plus a marker under `LANG=en_US.UTF-8`, and assert no marker.

## Finding 2 of 18: MEDIUM. A malformed snapshot file can pass `compare`, crash it, or give a false violation

**What.** The `[Unreleased]` CHANGELOG says compare "rejects a snapshot with a missing or wrongly typed field". `_load` checks only the top-level field types. Nested `head`, ref oids, element and value types, and nested submodule snapshots are not checked. Heidi and wendy found it (integration and release lanes).

**Evidence (confirmed).**
- `head` without `commit`: rc=0, `unchanged`.
- `head: {}`: rc=2, `unexpected KeyError: "'ref'"`.
- ref oid int: rc=2, `unexpected TypeError`.
- `dirty` value int: rc=1, a false `tracked` violation.
- A submodule entry `{}`, or one with bad refs: rc=1 `submodule`, never "malformed".
- `ignored_overflow` -1: rc=0.

**If unchanged.** The master writes these files itself, so the practical risk is low. But the CHANGELOG entry is false, and a corrupted snapshot can read as "unchanged". The problem is stable.

**Options.**
1. **Validate the full shape.** Check `head` as `{ref: str|None, commit: str}`, oids as str, each list element and dict value as str, `ignored_overflow > 20000`, and call `_load` recursively on each submodule. All failures go through `Fail("... is malformed: <field>")`. Benefit: the entry becomes true. Drawback: more validation code. Effort: S-M. Could break: valid snapshots, if a type rule is too strict.
2. **Narrow the CHANGELOG** to "a missing or wrongly typed top-level field". Benefit: tiny. Drawback: the silent-pass cases remain. Effort: S.
3. **Accept or defer.**

**Recommendation: option 1.** The fix is mechanical, and the "unexpected <Type>" exits already show the gap. Against it: the master is the only writer, so this guards against corruption more than against an attacker. Regression test: parametrize the mutations above and assert rc 2 with `is malformed`.

## Finding 3 of 18: MEDIUM. An ignored file's deletion is hidden when the run pushes the ignored count over 20000

**What.** If either snapshot is over the 20000 ignored-file cap, compare checks only ignored directories. A snapshot taken under the cap keeps a full list. Even so, adding 20001 ignored files during the run turns off the per-file check, and a deleted ignored file passes. Wendy and heidi found it (security and integration lanes).

**Evidence (confirmed).** Wendy's before snapshot had overflow `None` and `ignored ['secret.log']`. Wendy then created `ign/f0..f20000` and moved `secret.log`. `compare` gave `unchanged`, rc 0. Heidi's run: before had 20001 entries and no overflow. Heidi moved one file and touched two new ones, and `compare` gave rc=0 `unchanged`. SKILL.md lines 166-169 and the 0.3.1 CHANGELOG say deleted ignored files are detected. Only the docstring states the "either snapshot" limit.

**If unchanged.** A lane, or any process, can hide the deletion of a pre-existing ignored file by creating ignored files. It is easy to trigger by accident (`node_modules` installs). The problem is stable.

**Options.**
1. **Check before's list when before is under the cap.** When `before` has no `ignored_overflow`, check each file in its `ignored` with `os.path.lexists`, whatever state `after` is in. Benefit: closes the documented hole for the normal case. Drawback: one `lexists` per ignored file (at most 20000). Effort: S. Could break: nothing expected; a file moved into an `--allow` path still needs the allow check.
2. **Document the limit in SKILL.md and the CHANGELOG only.** Benefit: honest docs. Drawback: the hole stays. Effort: S.
3. **Accept or defer.**

**Recommendation: option 1, plus the doc line for the case where both snapshots are over the cap.** Against it: the reverse direction (before over the cap) still cannot be checked per file. Regression test: an ignored `secret.log`, then 20001 ignored files, then delete `secret.log`, and assert `("ignored-removed", "secret.log")`.

## Finding 4 of 18: MEDIUM. An unreadable untracked directory is skipped silently, and edits inside it pass

**What.** The docstring says an unreadable untracked file fails closed (exit 2). An untracked directory at mode 000 makes git print `warning: could not open directory` to stderr. `_run_git` drops that stderr on exit 0, so the directory and its contents are never recorded. Walter and wendy found it (journey and security lanes).

**Evidence (confirmed).** `mkdir lockd; echo original > lockd/f; echo keep > lockd/g; chmod 000 lockd`. `snapshot` gave rc=0 with `untracked []`. Then a chmod open, `TAMPERED > lockd/f`, `rm lockd/g`, chmod back. `compare` gave `unchanged`, rc=0. Control: an unreadable untracked file gives `cannot read u5: permission denied`, rc=2.

**If unchanged.** A lane, or a user's own private directory, can hide writes from the integrity check. The likelihood is low and the problem is stable. The mode-000 case stands in for a directory owned by another user.

**Options.**
1. **Fail on git's directory warnings.** Check `ls-files --others` stderr for `could not open directory`, and raise `Fail("cannot read <dir>/: ...")`. Benefit: also closes finding 13 (deep paths), since it is the same warning. Drawback: it depends on git's message text. Effort: S. Could break: repos that hold any unreadable directory can no longer be snapshotted (fail closed by design).
2. **`os.access` each top-level untracked entry.** Benefit: no stderr parsing. Drawback: misses nested unreadable directories and the deep-path case. Effort: S.
3. **Accept or defer.**

**Recommendation: option 1.** One check closes two findings. Against it: matching git's message text is brittle across git versions and locales (run git with `LC_ALL=C`). Regression test: `test_unreadable_untracked_directory_fails_closed`.

## Finding 5 of 18: MEDIUM. A snapshot hangs forever if a file is swapped for a fifo between `lstat` and `open`

**What.** `_fingerprint` calls `lstat`, sees a regular file, then calls a blocking `open()`. If the path became a fifo in between, the open blocks with no writer. The same function serves git-dir, untracked and dirty files. Trudy found it (security lane).

**Evidence (confirmed).** A swapper loop on `race/.git/agoge-swap` gave `ok=39 hang(timeout 5s)=1` in run 1 and `ok=7 hang=1` in run 2. The traceback stopped at `_fingerprint` line 342, `with open(full, "rb")`.

**If unchanged.** A process running alongside can hang the master's integrity check, and the agoge run stalls. This needs a deliberate race, so it is unlikely by accident. The problem is stable.

**Options.**
1. **Open safely and verify.** Use `os.open(full, O_RDONLY|O_NOFOLLOW|O_NONBLOCK)`, then `fstat`, and require `S_ISREG` with the same `st_ino`/`st_dev` as the `lstat`. Otherwise return `special:`. Benefit: closes the window. Drawback: slightly more code. Effort: S. Could break: nothing expected; non-blocking reads on regular files behave normally.
2. **Add a timeout to the whole command.** Benefit: bounds every hang. Drawback: it hides the cause and turns a hang into exit 2. Effort: S.
3. **Accept or defer.**

**Recommendation: option 1, with option 2 as a backstop through finding 9.** Against it: a race test is flaky, so the test should monkeypatch `os.lstat` to lie rather than race.

## Finding 6 of 18: MEDIUM. Run against a linked worktree, the check misses a branch switch in the main worktree

**What.** `take_snapshot` records worktree HEADs for every worktree except the first entry of `git worktree list`. The code assumes that entry is the repo itself, but it is always the main worktree. When `<repo>` is a linked worktree, the main worktree's HEAD is never recorded. Heidi found it (integration lane).

**Evidence (confirmed).** `snapshot c9/m-wt` recorded `worktree_heads` keys holding only `m-wt`. Then `checkout -q other` ran in the main worktree. `compare` gave rc=0 `unchanged`. A detached checkout also gave rc=0.

**If unchanged.** When agoge targets a linked worktree, a lane can switch the main checkout's branch unseen. The likelihood is low and the problem is stable.

**Options.**
1. **Skip by path, not by position.** Record HEAD for every worktree whose path is not `repo`. Benefit: correct for both kinds of target. Drawback: none known. Effort: S. Could break: path normalization (`/private/tmp` against `/tmp` realpaths).
2. **Refuse a linked worktree as target** (exit 2). Benefit: simple. Drawback: removes a real use case. Effort: S.
3. **Accept or defer.**

**Recommendation: option 1.** Against it: realpath normalization must match git's output, or the repo itself starts reporting `worktree-head`. Regression test: `snapshot_from_linked_worktree_catches_main_worktree_checkout`.

## Finding 7 of 18: MEDIUM. Every snapshot reads the whole Git LFS object store

**What.** The git-dir walk fingerprints every file under `.git/lfs/objects`, and reads each one in full up to 64 MiB. A repo with gigabytes of LFS objects costs gigabytes of reads on each of the three or more snapshots per run. Peggy found it (performance lane).

**Evidence (confirmed).** For 8 objects of 60 MiB: `bytes_read: 503343508`. For 16: `bytes_read: 1006659988`. That is linear, about one byte read per byte stored. 8272b8e read the same bytes; the PRDs fixed memory (85 to 29 MiB) but not the reads. No budget is stated, so this is an observation-only number.

**If unchanged.** agoge runs on LFS-heavy repos get slow, and the cost grows with the store. The likelihood depends on the user's repos.

**Options.**
1. **Fingerprint `lfs/` (and `annex/`) by size and mtime only.** Benefit: keeps some change detection at near-zero cost. Drawback: a same-size, same-mtime rewrite goes unseen. Effort: S. Could break: nothing expected.
2. **Add `lfs` to `GITDIR_UNCHECKED`.** Benefit: simplest. Drawback: no detection inside the LFS store at all. Effort: S.
3. **Accept or defer.**

**Recommendation: option 1.** LFS objects are content-addressed, so a rewrite that keeps size and mtime is not a realistic change. Against it: it adds a third fingerprint mode. Regression test: count bytes read through a wrapped `open` while N doubles.
